# Техническое задание: StorePrice — мобильное приложение учёта товаров и цен

## 1. Роль и задача
Ты — senior Android-разработчик и архитектор приложений. Твоя задача — самостоятельно разработать полноценное, работающее Android-приложение для небольшого продуктового магазина.

Работай непосредственно с файлами проекта через OpenCode. Не ограничивайся планированием, примерами кода или макетами. Создавай приложение, запускай сборку, выполняй тесты, исправляй ошибки и подготавливай APK для установки на реальный Android-телефон.

Пользователь разрабатывает приложение на Linux Mint, используя OpenCode. Android Studio не является обязательным инструментом разработки. Все операции должны быть доступны через терминал, Gradle Wrapper и Android SDK.

Основной язык интерфейса — русский.

Название проекта: StorePrice.

## 2. Цели приложения

Приложение предназначено для совместной работы более пяти сотрудников магазина с единым каталогом товаров.

Необходимые возможности:

1. Сканирование товарных штрихкодов камерой.
2. Добавление товаров со штрихкодом и без него.
3. Изменение названий и цен.
4. Удаление товаров.
5. Мгновенный поиск по названию и штрихкоду.
6. Общая облачная база товаров для всех сотрудников.
7. Автоматическое обновление данных на других устройствах.
8. Push-уведомления при изменении цены другим сотрудником.
9. Работа без интернета с доступом к последней синхронизированной копии товаров.
10. Безопасная авторизация и разграничение прав.
11. История изменения цен.
12. Экспорт и импорт каталога.

Приложение должно быть простым, быстрым и пригодным для повседневного использования в магазине.

## 4. Архитектура

Используй следующую схему:

Android UI → ViewModel → Repository → Room и Supabase.

Room является локальным источником данных для интерфейса. Supabase хранит общую актуальную версию каталога.

Все экраны, включая поиск, должны получать данные из локальной базы. Серверная синхронизация обновляет Room, а интерфейс автоматически реагирует на изменения.

При подключении к интернету приложение синхронизирует изменения с сервером и получает обновления от других сотрудников.

Realtime применяется для обновления каталога, когда приложение активно. FCM применяется для системных уведомлений, в том числе в фоновом режиме.

Все критические операции, проверка прав и фиксация истории выполняются на сервере. Не полагайся только на проверки в Android-клиенте.

## 5. Модель данных

### 5.1. Таблица products

Поля:

- id: UUID, первичный ключ.
- barcode: nullable text.
- name: text, обязательное поле.
- price_kzt: BIGINT, неотрицательная цена в целых тенге.
- is_deleted: boolean для логического удаления либо эквивалентный безопасный механизм.
- created_at: timestamp.
- updated_at: timestamp.
- updated_by: UUID пользователя.
- version: целое число или эквивалентный механизм контроля конкурентных изменений.

Требования:

- Штрихкод может отсутствовать.
- Пустые строки штрихкода преобразуются в NULL.
- Непустой штрихкод должен быть уникальным среди неудалённых товаров.
- Штрихкод хранить как текст, чтобы сохранять ведущие нули.
- Название после обрезки пробелов не может быть пустым.
- Цена хранится целым числом тенге.
- Все даты на сервере должны иметь однозначную временную зону, предпочтительно UTC.
- Логическое удаление необходимо для корректного распространения удаления на другие устройства.

### 5.2. Таблица profiles

Поля:

- id: UUID, связанный с Supabase Auth.
- display_name: имя сотрудника.
- role: admin или employee.
- is_active: boolean.
- created_at: timestamp.

Пользователь должен быть деактивируемым без потери истории его действий.

Публичная самостоятельная регистрация по умолчанию отключена. Администратор создаёт или приглашает сотрудников.

### 5.3. Таблица price_history

Поля:

- id: UUID.
- product_id: UUID.
- product_name_snapshot: название на момент изменения.
- old_price_kzt: BIGINT.
- new_price_kzt: BIGINT.
- changed_by: UUID.
- changed_at: timestamp.
- operation_id: UUID для идентификации операции.
- device_id: nullable идентификатор установки приложения.

Запись истории должна сохраняться автоматически серверной логикой, а не формироваться исключительно Android-клиентом.

Хранить историю изменения цены, включая изменение на нулевую цену, если оно разрешено бизнес-правилами. Отдельно обрабатывать создание и удаление товара.

### 5.4. Таблица device_tokens

Поля:

- id: UUID.
- user_id: UUID.
- fcm_token: text.
- device_id: text.
- is_active: boolean.
- updated_at: timestamp.

Один сотрудник может иметь несколько устройств. Устаревшие токены должны деактивироваться.

### 5.5. Дополнительные таблицы

Создай при необходимости:

- sync_state — состояние синхронизации устройства.
- notification_events — журнал постановки уведомлений в очередь, попыток и статусов доставки.
- audit_log — журнал важных административных действий.
- import_jobs — состояние импорта каталога.

Не усложняй схему без практической необходимости.

## 6. Авторизация и роли

### Администратор

Может:

- Добавлять и деактивировать сотрудников.
- Просматривать каталог.
- Добавлять и редактировать товары.
- Изменять цены.
- Удалять и восстанавливать товары.
- Просматривать историю изменений.
- Импортировать и экспортировать каталог.

### Сотрудник

Может:

- Искать товары.
- Сканировать штрихкоды.
- Просматривать цены.
- Добавлять товары.
- Редактировать название и цену.
- Просматривать историю изменений.

По умолчанию сотрудник не может управлять пользователями и административными настройками.

Разрешения должны проверяться на сервере через RLS и серверные функции. Нельзя позволять клиенту самостоятельно назначать себе роль admin.

### Способ входа

Вход выполняется по номеру телефона и паролю через Supabase Auth. Публичная самостоятельная регистрация отключена: сотрудника создаёт администратор, подтверждает телефон и активирует профиль. Пароли хранит и проверяет Supabase Auth; приложение не хранит пароль в открытом виде.

Телефонные номера могут переиспользоваться операторами связи, поэтому при увольнении сотрудника его профиль деактивируется, а не удаляется вместе с историей. Смена пароля и восстановление доступа выполняются администратором.

Реализовать вход, выход и обработку истечения сессии.

## 9. Добавление товара

Создать отдельную форму добавления товара.

Поля:

- Название — обязательно.
- Цена в тенге — обязательно.
- Штрихкод — необязателен.

Поддержать два сценария.

### Ручное добавление

Пользователь нажимает «Добавить товар», вводит название и цену, при необходимости указывает штрихкод и сохраняет товар.

### Добавление сканированием

1. Пользователь открывает сканер.
2. Камера распознаёт штрихкод.
3. Приложение проверяет локальный каталог.
4. Если товар существует, открывается его карточка.
5. Если товар отсутствует, открывается форма добавления с заполненным штрихкодом.

При отсутствии интернета новый товар не должен создавать ложное впечатление, что он уже добавлен в общую базу. Если создание офлайн не поддерживается, объяснить это и предложить повторить действие после восстановления соединения.

Не допускать повторной обработки одного штрихкода за одну сессию сканирования.

- Возможность вернуться на главный экран.
- Остановка камеры при уходе с экрана.

Сканирование должно выполняться на устройстве, без обязательного обращения к внешнему серверу.

## 11. Карточка товара и редактирование

В карточке отображать:

- Название.
- Штрихкод.
- Текущую цену.
- Время последнего изменения.
- Имя сотрудника, который последним изменил цену, если данные доступны.
- Доступные действия в соответствии с ролью.

Редактирование должно позволять изменять название, цену и штрихкод.

Перед сохранением проверять:

- Валидность цены.
- Непустое название.
- Отсутствие дублирующего штрихкода.
- Актуальность версии записи при наличии конкурирующих изменений.

Если другой сотрудник изменил товар одновременно, не перезаписывать его изменение молча. Показать конфликт и предложить загрузить актуальную версию либо повторить редактирование.

Удаление требует подтверждения.

Предпочтительно использовать логическое удаление с сохранением истории и распространением статуса удаления на все устройства.

## 12. История цен

Создать отдельный экран истории изменений.

Для каждой записи показывать:

- Название товара.
- Старую цену.
- Новую цену.
- Имя сотрудника.
- Дату и время.
- Размер изменения в тенге.

Предусмотреть сортировку от новых записей к старым.

При открытии истории конкретного товара показывать только изменения этого товара.

Историю нельзя редактировать или удалять обычным сотрудникам.

История цены должна фиксироваться атомарно вместе с изменением основной записи.

При создании нового товара отдельное событие создания можно хранить в журнале аудита; не имитировать несуществующую старую цену.

## 13. Общая база и синхронизация

Реализовать полноценный механизм синхронизации между Room и Supabase.

### При запуске

1. Отобразить локальный каталог, если он уже имеется.
2. Проверить наличие интернет-соединения.
3. Получить актуальные данные с сервера.
4. Обновить локальную базу.
5. Обновить время последней успешной синхронизации.

Не блокировать просмотр локального каталога до завершения сетевого запроса.

### При изменении на другом устройстве

1. Supabase сохраняет изменение.
2. Realtime сообщает подключённым устройствам об изменении.
3. Клиент получает актуальную запись.
4. Room обновляется.
5. Интерфейс автоматически отображает новую цену.

Для больших каталогов использовать постраничную загрузку или инкрементальную синхронизацию по времени и версии. Не скачивать все товары при каждом обновлении.

Удаления также должны синхронизироваться через логические отметки или другой корректный механизм.

### Обработка ошибок

- Повторять временно неудачные запросы с ограниченным экспоненциальным увеличением задержки.
- Не создавать дубликаты при повторной отправке запроса.
- Обрабатывать истечение авторизации.
- Отображать ошибки без потери локального каталога.
- Не объявлять синхронизацию успешной до фактического подтверждения сервера.

## 14. Офлайн-режим

Это обязательная функция.

Если интернет пропал, пользователь должен иметь возможность:

- Открыть приложение.
- Просматривать ранее синхронизированные товары.
- Искать по названию и штрихкоду.
- Сканировать штрихкод камерой.
- Открывать карточки товаров.
- Видеть последнюю сохранённую цену.
- Видеть время последней успешной синхронизации.

В офлайн-режиме показывать заметную, но ненавязчивую отметку «Нет соединения» и предупреждение, что цены могут быть устаревшими.

Для первой версии разрешить изменение цен и добавление товаров только при доступном интернете.

При попытке сохранить изменения офлайн показать понятное сообщение и не потерять введённые пользователем данные в форме.

После восстановления соединения автоматически возобновить синхронизацию.

Архитектуру подготовить к будущему офлайн-редактированию через очередь операций, но не реализовывать сложную очередь изменений в MVP, если она не требуется для надёжной работы остальных функций.

Push-уведомления и получение чужих изменений без интернета невозможны. После восстановления связи приложение должно получить актуальное состояние.

## 15. Push-уведомления об изменении цены

Использовать Firebase Cloud Messaging.

Уведомления отправляются только после успешного изменения цены на сервере.

Сценарий:

1. Сотрудник меняет цену товара.
2. Сервер проверяет права и сохраняет новую цену.
3. В той же транзакции фиксируется запись истории и создаётся событие уведомления либо гарантированно создаваемая запись в transactional outbox.
4. Серверный обработчик отправляет FCM-уведомления.
5. Остальные активные устройства получают уведомление.
6. Устройство сотрудника, совершившего изменение, не получает собственное уведомление об этой операции.

Уведомление содержит:

- Название товара.
- Старую цену.
- Новую цену.
- Имя сотрудника.
- Время изменения.

Пример:

«Изменилась цена: Кофе Nescafe. Было 1 200 ₸, стало 1 350 ₸. Изменил: Иван».

Не включать в уведомления секретные сведения и персональные данные сверх необходимого.

Требования:

- Уведомления должны работать, когда приложение закрыто, в пределах возможностей Android и FCM.
- Обработать разрешение на уведомления на Android 13 и новее.
- Создать Android notification channel.
- При нажатии на уведомление открывать карточку нужного товара.
- Не отправлять уведомление, если цена фактически не изменилась.
- Не отправлять несколько одинаковых уведомлений из-за повторной обработки одного события.
- Учитывать несколько устройств одного сотрудника.
- Обрабатывать недействительные FCM-токены.
- Предусмотреть журнал ошибок отправки и повторные попытки.
- Не утверждать, что уведомление гарантированно доставлено только потому, что FCM принял запрос.

Для надёжности использовать серверный обработчик и transactional outbox или эквивалентный механизм, исключающий потерю события при сбое между фиксацией цены и отправкой уведомления.

Секреты Firebase Service Account и серверные ключи хранить только в защищённой серверной среде. Не помещать их в Android-проект.

FCM-токены не считать средством авторизации.

На первом этапе уведомлять обо всех изменениях цены всем остальным активным сотрудникам. Изменения названия, добавление и удаление можно показывать через Realtime; отдельные push-уведомления об этих событиях сделать опциональными.

## 16. Импорт и экспорт товаров

Предусмотреть импорт и экспорт CSV.

Импорт должен:

- Поддерживать название, цену и штрихкод.
- Проверять корректность данных.
- Обрабатывать товары без штрихкодов.
- Выявлять дубликаты штрихкодов.
- Показывать предварительный отчёт об ошибках до применения изменений.
- Не создавать частично импортированный каталог без понятного отчёта.
- Выполняться только пользователем с разрешёнными правами.

Экспорт должен включать название, штрихкод и цену.

Не экспортировать секреты, токены или данные авторизации.

Если Excel/XLSX не входит в MVP, реализовать надёжный CSV с UTF-8 и корректной обработкой русского языка. Архитектура должна позволять добавить XLSX позднее.

## 17. Безопасность

Обязательные требования:

- Включить RLS на всех пользовательских таблицах.
- Запретить анонимный доступ к каталогу и истории.
- Проверять пользователя и его роль на сервере.
- Не позволять пользователю менять собственную роль через клиент.
- Защитить регистрацию сотрудников.
- Ограничить права на изменение, удаление и восстановление товаров.
- Не раскрывать Service Role Key в приложении.
- Не хранить пароли в открытом виде.
- Использовать HTTPS.
- Не логировать пароли, токены и секретные ключи.
- Проверять входные данные на клиенте и сервере.
- Проверять конкурентные изменения.
- Ограничить доступ к FCM-токенам конкретными пользователями.
- Предусмотреть деактивацию учётной записи сотрудника.
- Обеспечить, чтобы деактивированный сотрудник больше не мог выполнять защищённые операции.

Не использовать service-role ключ для обычных операций Android-клиента.

Не объявлять точные показатели производительности подтверждёнными без реальных измерений.

## 21. Среда разработки и сборка

Сначала проверь Linux Mint и доступные инструменты.

Проверь:

- Java/JDK.
- Android SDK.
- Gradle Wrapper.
- Наличие телефона или возможности подключения через ADB.
- Версии инструментов и совместимость зависимостей.

Если среда не настроена, подготовь конкретные инструкции по установке необходимых компонентов без требования устанавливать Android Studio.

Не изменяй системные настройки и не устанавливай большие пакеты без необходимости и объяснения пользователю.

Используй Gradle Wrapper, включённый в проект.

Основная команда сборки:

./gradlew assembleDebug

Основная команда тестирования:

./gradlew testDebugUnitTest

Запускай сборку и доступные тесты, исправляй ошибки.

Готовый APK должен находиться в стандартном каталоге:

app/build/outputs/apk/debug/app-debug.apk

Не заявляй, что APK создан, пока не проверишь наличие фактического файла.

Дополнительно подготовь инструкцию установки на Android через USB с помощью ADB и альтернативную инструкцию копирования APK на телефон.

## 25. Критерии готовности

MVP считается реализованным, если:

1. Проект собирается в APK через Gradle Wrapper.
2. Пользователь может войти в приложение.
3. Товары добавляются, редактируются и удаляются.
4. Работает ручное добавление без штрихкода.
5. Камера распознаёт распространённые товарные штрихкоды.
6. Поиск работает локально без интернета.
7. Несколько пользователей работают с одной общей базой.
8. Изменение цены появляется на других подключённых устройствах.
9. История содержит правильные старую и новую цены и автора.
10. Push-уведомления реализованы серверным способом и проверены в доступном окружении.
11. Офлайн-каталог сохраняется после перезапуска приложения.
12. При восстановлении интернета данные синхронизируются.
13. RLS запрещает неавторизованный доступ.
14. Секретные ключи не попадают в APK.
15. Основные тесты проходят.
16. Документация позволяет повторить настройку и сборку.

Если некоторые критерии невозможно проверить без реального Supabase-проекта, Firebase-проекта или телефона, прямо перечисли их в итоговом отчёте. Не выдавай заглушки за работающие функции.
