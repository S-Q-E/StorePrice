# StorePrice — инструкции для разработки

## Назначение проекта

StorePrice — Android-приложение для небольшого продуктового магазина: общий каталог товаров, цены в тенге, поиск, сканирование штрихкодов, история цен, офлайн-доступ, синхронизация и push-уведомления.

Основной язык интерфейса — русский. Все цены хранятся целыми числами в тенге (`BIGINT` / `Long`).

## Текущий этап

Этапы 3 и 4 завершены. Этап 3 проверен на физическом телефоне: сканирование, добавление товара и повторное открытие карточки. Этап 4 проверен пользователем на телефоне: успешный вход, общий каталог, запись через RPC и офлайн-режим работают. Живой проект Supabase `zhqvrzowbvkeurikjatf` настроен; миграции `001`, `002`, `003` и `004` применены, Phone provider включён, публичная регистрация отключена, первый администратор создан. `003_hardening.sql` применена 2026-11-13: RLS-политики, права функций и серверная проверка роли `42501` проверены. Публичные URL/key лежат в `local.properties`; `supabase_admin.env` с PAT, secret key и паролем администратора игнорируется Git. Секреты в APK и Git не попадают.

**Этап 5 реализован локально:** начальная и инкрементальная синхронизация по курсору `updated_at`, Room как источник данных для UI, Realtime-триггер при активном приложении, автоматическая синхронизация при восстановлении сети, индикатор сети, время последней успешной синхронизации и ручное обновление каталога. Чтение каталога повторяется с ограниченным экспоненциальным backoff; записи из UI автоматически не повторяются, чтобы не создавать дубликаты. Legacy-выгрузка использует локальный UUID как `p_id` и идемпотентна: `003_hardening.sql` применена. Редактировать каталог может только администратор: UI скрывает действия, репозиторий блокирует записи, сервер возвращает `42501`. Миграция `004_realtime.sql` применена к живому проекту, publication `products` проверена; живая доставка событий на двух устройствах, роли на телефоне и режим полёта на текущем APK ещё впереди. WorkManager и очередь офлайн-записей не реализованы.

**Этап 6 реализован локально:** Firebase Messaging, условное подключение `google-services`, стабильный `device_id`, регистрация/снятие FCM-токена, канал `price_changes`, разрешение Android 13+, парсинг payload и переход в карточку товара; на сервере — transactional outbox `notification_events`/`notification_deliveries`, триггер на `price_history`, retry/backoff, исключение автора и Edge Function `send-price-notifications`. Firebase-проекта, `google-services.json`, service account, применённой миграции `005`, деплоя worker и живой FCM-проверки пока нет. Сборка, 134 unit-теста и lint проходят. Инструкция: `docs/PUSH_NOTIFICATIONS.md`.

**Не подтверждено отдельно:** полная матрица форматов сканера, автофокус, освещение, отзыв разрешения, отсутствие камеры и логи освобождения камеры на телефоне. Это дополнительные ручные проверки, основной сценарий сканера закрыт.

## Окружение

Инструменты установлены локально для пользователя, без `sudo`, Android Studio и изменений системы:

```bash
source scripts/android-env.sh
```

- JDK: Temurin 17.0.21+9, `~/.local/opt/jdk-17.0.21+9`
- Android SDK: `~/android-sdk` (`platforms;android-35`, `build-tools;35.0.0`, `platform-tools`)
- Эмулятор: 37.2.12, system image `system-images;android-35;default;x86_64`, AVD `storeprice_test` (Android 15)
- Gradle: 8.9, `~/.local/opt/gradle-8.9`; в проекте используется Gradle Wrapper 8.9
- `local.properties` содержит `sdk.dir` и публичные `SUPABASE_URL`/publishable key; не коммитится
- `/dev/kvm` доступен пользователю через ACL; эмулятор запускается с программной графикой

## Правила разработки

1. **Не перескакивать этапы.** Не начинать Room, сканер, Supabase, FCM, пока предыдущий этап не собран и не проверен.
2. **Не перезаписывать пользовательские файлы.** Перед крупными изменениями проверять `git status` и содержимое каталогов.
3. **Секреты не попадают в Git и APK.** `SUPABASE_SERVICE_ROLE_KEY`, Supabase PAT, `supabase_admin.env`, Firebase service account и любые приватные ключи запрещены в Android-модуле и Git. Публичный anon/publishable key — только через локальную конфигурацию.
4. **Room — источник данных для UI.** Экраны и поиск читают локальную базу; сеть обновляет Room, а не UI напрямую.
5. **Сервер — источник правды для прав и истории.** RLS и серверные функции обязательны; клиентские проверки роли недостаточны.
6. **Схема Room версионируется.** Схемы лежат в `app/schemas/`; после изменения сущностей — новая версия БД и миграция. Не использовать destructive fallback.
7. **Штрихкод уникален среди активных товаров.** Пустой штрихкод — `NULL`; ведущие нули сохранять. Удаление — логическое, чтобы штрихкод можно было переиспользовать.
8. **UI на русском.** Строки — в `res/values/strings.xml`, без «рыбных» товаров в рабочей базе.
9. **Цены — целые тенге.** Не использовать `Double` для денег.
10. **Минимальные зависимости.** Добавлять библиотеку только под конкретную задачу этапа, проверяя совместимость версий.
11. **Документация — часть результата.** После этапа обновлять `CURRENT_STATUS.md` и, при необходимости, `ARCHITECTURE.md`/`ROADMAP.md`/`docs/TESTING.md`.
12. **Не выдавать заглушки за реализацию.** В отчёте явно разделять: работает / не проверено / не реализовано.

## Стиль кода

- Kotlin, Gradle Kotlin DSL, version catalog (`gradle/libs.versions.toml`).
- MVVM: `ui` → `ViewModel` → `Repository` → `Room`/`Supabase`.
- Coroutines и `Flow`; UI-состояние иммутабельное.
- Пакеты по слоям внутри `com.storeprice.app` (`core`, `data`, `domain`, `ui`).
- Публичные функции и нетривиальная логика — с KDoc; бизнес-правила покрывать unit-тестами.
