## Что работает

### Каталог (этап 2)

- Локальный каталог товаров на Room: список, пустое состояние, загрузка.
- Добавление товара: обязательное название, целая цена в тенге, необязательный штрихкод.
- Редактирование названия, цены и штрихкода.
- Логическое удаление с подтверждением; товар исчезает из списка, карточки и поиска.
- После удаления карточка не показывает кратковременное «Товар не найден»: при `deleted = true` или `isDeleting` с уже исчезнувшим товаром показывается нейтральная загрузка до навигации.
- Уникальность штрихкода среди активных товаров; пустой штрихкод сохраняется как `NULL`; ведущие нули сохраняются.
- Повторное использование штрихкода после логического удаления.
- Локальный поиск по названию и штрихкоду без учёта регистра и лишних пробелов.
- Сортировка каталога по названию через `java.text.Collator` (`ru_KZ`, `SECONDARY`): казахские буквы не уходят после «Я».
- Приоритет поиска: точный штрихкод → точное название → префикс штрихкода → префикс названия → вхождение; внутри группы — сортировка по Collator, затем по `id`.
- Русский интерфейс на Compose Material 3, светлая и тёмная темы.
- Сохранение данных после перезапуска приложения и повторной установки APK.
- Room schema v1 экспортирована в `app/schemas/`.

### Сканер (этап 3)

- Кнопка сканера в верхней панели каталога; отдельный маршрут `scanner`.
- Запрос разрешения `CAMERA` при входе и обработка отказа: объяснение, повторный запрос и переход в настройки приложения.
- Обработка отсутствия камеры отдельным экраном.
- CameraX-предпросмотр, визуальная рамка сканирования и инструкция на русском.
- Локальное распознавание ML Kit без обязательного сервера: EAN-13, EAN-8, UPC-A, UPC-E, Code 128, Code 39, Code 93, ITF и Codabar.
- Защита от повторной обработки: первый распознанный код блокирует сессию, пока выполняется поиск или уже есть результат.
- Повтор одного и того же кода в соседних кадрах дополнительно подавляется в анализаторе.
- Поиск по точному активному штрихкоду без учёта регистра, с trim и сохранением ведущих нулей; удалённые товары не возвращаются.
- Найденный товар → карточка товара.
- Неизвестный код → форма нового товара с заполненным штрихкодом.
- Камера привязана к lifecycle экрана и освобождается при уходе; при ошибке запуска есть повтор.
- ML Kit добавляет в объединённый manifest разрешения `INTERNET` и `ACCESS_NETWORK_STATE`; модель распознавания входит в APK. С этапа 4 приложение также использует сеть для Supabase Auth, но сам сканер остаётся офлайн.

### Общий каталог (этап 4, реализовано)

- UI по-прежнему читает только Room: список, карточка, поиск и сканер работают с локальным кэшем.
- При открытии каталога выполняется начальная полная синхронизация: PostgREST читает `products` постранично по 1000 строк, включая логически удалённые записи, и заменяет локальный снимок в одной транзакции Room.
- Если в Room остались товары, созданные до подключения общей базы, они один раз выгружаются через `create_product`; при совпадении активного штрихкода побеждает серверная запись. Это защищает локальный каталог от молчаливой потери данных.
- Ошибка сети, 401/403 или серверная ошибка не очищают Room: каталог продолжает показывать последний успешный снимок.
- Создание, изменение и логическое удаление выполняются серверными RPC `create_product`, `update_product`, `soft_delete_product`; после успешного ответа серверная строка записывается в Room.
- Для изменения и удаления используется `version` из Room. Конфликт версий показывается в форме, после чего выполняется повторная синхронизация; дубликат штрихкода, отсутствие товара, офлайн и серверная ошибка различаются в UI.
- Первая версия не ставит изменения в очередь: при `isOffline` кнопки добавления, редактирования и удаления скрыты, форма из неизвестного штрихкода не открывается, а неудачное сохранение не теряет введённые значения.
- Бейдж каталога изменён на «Общий каталог».
**Проверено пользователем на телефоне:** успешный вход, общий каталог, запись через RPC и офлайн-режим. **Проверено локально:** 17 unit-тестов `SyncingProductRepositoryTest` (полный и инкрементальный sync, курсор, backoff, отсутствие автоматических повторов записи из UI, legacy-выгрузка с `p_id`, create/update/delete, версии и ошибки), 7 тестов маппинга серверной строки и ошибок PostgREST, 8 тестов формы. Сборка, 116 тестов и lint проходят.

**Не проверено:** деактивация сотрудника, смена роли, refresh после истечения токена, конфликт версий между двумя устройствами на живом проекте и поведение при долгом отсутствии сети.

### Синхронизация и офлайн (этап 5, реализовано)

- `ProductRemote.fetchAll()` читает каталог keyset-пагинацией `id > lastId` с `limit=1000`, включая мягко удалённые строки.
- Первый успешный sync заменяет Room полным снимком; последующие вызовы используют `fetchSince(cursor)` и upsert’ят только строки с `updated_at >= cursor`.
- Курсор — максимальный серверный `updated_at`; хранится вместе со временем последней успешной синхронизации в приватном `SharedPreferences` (`SharedPreferencesSyncMetadataStore`). Схема Room не менялась.
- Если курсор есть, а локальная таблица пуста, выполняется полный sync для восстановления.
- Курсор двигается только после успешной транзакции Room. Ошибка сети/сервера сохраняет и строки, и старый курсор.
- `SyncRetryPolicy` повторяет только чтение каталога: до 3 попыток с задержками 0,5 с и 1 с и ограничением 4 с. `Unauthorized` не повторяется; записи из UI автоматически не повторяются.
- `ProductRealtimeSource` подписывается на Postgres Changes `public.products`; событие только запускает инкрементальный sync, данные перечитываются через PostgREST/RLS.
- Выгрузка legacy-товаров передаёт локальный UUID как `p_id`. Если к проекту ещё не применена `003_hardening.sql`, клиент по ошибке «function not found» один раз повторяет create без `p_id`; выгрузка продолжает работать, но идемпотентность на этом сервере недоступна.
- Realtime работает только в foreground через `ProcessLifecycleOwner` + `repeatOnLifecycle(STARTED)`; при уходе в background канал снимается.
- `NetworkMonitor` слушает `ConnectivityManager`; при восстановлении сети выполняется тихая проверка сессии и инкрементальная синхронизация. После возврата в foreground Realtime переподключается.
- В каталоге появились индикатор сети, время последней успешной синхронизации, состояние «Обновление каталога…» и кнопка ручного обновления.
- При офлайне каталог и поиск работают из Room, показывается предупреждение о сохранённых данных и возможной устарелости цен, кнопки изменения скрыты.
- Миграция `supabase/migrations/202611120004_realtime.sql` применена к живому проекту 2026-11-12: `public.products` входит в publication `supabase_realtime`, RLS включена. Доставка событий на двух устройствах ещё не проверена.
- WorkManager, фоновая синхронизация и очередь офлайн-записей не реализованы.

### Вход в Android (этап 4, реализовано)

- Экран входа на русском: номер телефона, пароль, показ/скрытие пароля, ошибки, состояние загрузки.
- Нормализация номера к E.164: `8 700 123-45-67`, `+7 (700) 123-45-67`, `77001234567` и 10 цифр без кода страны.
- Supabase Auth с входом по телефону и паролю; `supabase-kt` 3.0.0 и Ktor OkHttp.
- Восстановление сохранённой сессии при запуске, автоматический refresh средствами `auth-kt`.
- После входа и при обновлении сессии читается `public.profiles`: роль, имя и `is_active`.
- Интерактивный вход не читает сессию после `signInWith`: результат проверки профиля передаётся из коллектора через `Deferred` под общим `profileCheckMutex`. Порядок событий не влияет на `AccountInactive`, `AccountNotFound`, `NetworkError` и `ServerError`.
- Неактивный профиль, отсутствующий профиль и истёкшая сессия разлогинивают пользователя и показывают понятное сообщение.
- Активный профиль кэшируется в приватном `SharedPreferences` (`storeprice_profile_cache`): id, имя, роль, `isActive` и время проверки. Пароль и токены в этот файл не попадают.
- При сетевой ошибке или ответе 5xx проверка профиля использует кэш того же пользователя не старше 30 дней: каталог открывается, состояние — `SignedIn(isOffline = true)`. Экран недоступности остаётся только при отсутствии или устаревании кэша.
- То же правило применяется к `SessionStatus.RefreshFailure`; идентификатор пользователя берётся из текущей или сохранённой сессии.
- Кэш очищается при выходе, неактивном или отсутствующем профиле, ответе 401 и смене пользователя.
- При возврате приложения на передний план выполняется тихая повторная проверка не чаще одного раза в 5 минут; успешная проверка снова ставит `isOffline = false`.
- В каталоге при `isOffline` показывается узкий баннер «Нет связи: показаны сохранённые данные». `NavHost` и Room-каталог при переходе в офлайн не пересоздаются.
- Выход из меню аккаунта в каталоге; пароль приложением не сохраняется.
- Access/refresh token хранятся в приватных `SharedPreferences`; `allowBackup=false`, cloud backup и device transfer запрещены.
- Без `SUPABASE_URL`/ключа приложение не падает, а показывает сообщение о незавершённой настройке.
- Обработаны серверные коды `invalid_credentials`, `phone_provider_disabled`, `phone_not_confirmed`, `user_banned` и rate limit.
- Публичный URL и publishable key читаются из игнорируемого `local.properties` и попадают в `BuildConfig`; `service_role` не используется.

**Проверено пользователем на телефоне:** успешный вход администратора, чтение профиля, общий каталог и офлайн-режим. **Проверено локально:** unit-тесты, сборка, lint, запуск экрана входа на эмуляторе Android 15, локальная валидация телефона/пароля, а также реальный запрос к Supabase с ответом `phone_provider_disabled` до настройки проекта. Офлайн-ветки проверены unit-тестами `AuthSessionControllerTest`, порядок «коллектор раньше signIn» — `SupabaseAuthRepositoryTest`.

**Не проверено:** деактивация сотрудника во время сессии, смена роли, принудительный refresh после истечения токена и отдельная проверка выхода на живом проекте.

#### Миграция 004: Realtime для products (применена 2026-11-12)

`supabase/migrations/202611120004_realtime.sql` применена к `zhqvrzowbvkeurikjatf` 2026-11-12 через Management API. На временной PostgreSQL 17 миграция применена дважды; локальное предупреждение о `wal_level` относится к тестовой базе без логической репликации, не к hosted Supabase.

Процедура ниже остаётся для нового проекта или повторной проверки:

1. Открыть **SQL Editor** живого проекта.
2. Выполнить содержимое `202611120004_realtime.sql`.
3. Проверить публикацию:

```sql
select pubname, schemaname, tablename
from pg_publication_tables
where pubname = 'supabase_realtime'
  and schemaname = 'public'
  and tablename = 'products';

select pubname, pubinsert, pubupdate, pubdelete, pubtruncate
from pg_publication
where pubname = 'supabase_realtime';
```

Ожидается строка `products` и включённые операции insert/update/delete. Без этой миграции клиент подключится к Realtime-каналу, но события таблицы `products` приходить не будут. Клиент не применяет payload напрямую, а запускает инкрементальный sync через PostgREST.

5. **Модель устройства не зафиксирована.** Проверка выполнена пользователем на его телефоне; точная модель и версия Android в документации не указаны.
6. **Живой Auth проверен в Android на телефоне.** Phone provider включён, публичная регистрация отключена, первый администратор создан; пользователь подтвердил успешный вход, общий каталог, запись через RPC и офлайн-режим.
7. **Миграции применены к живому Supabase не полностью.** `001`/`002` созданы; `004_realtime.sql` применена и publication проверена; `003_hardening.sql` пока не применена. Деактивация сотрудника, смена роли, refresh, запрет прямых INSERT/UPDATE и неизменяемость истории цен через реальный JWT ещё не проверены.
8. **Realtime-публикация включена, но доставка событий не проверена на устройствах.** `public.products` входит в `supabase_realtime`, RLS включена; код подписки готов. Без живой проверки двух устройств нельзя утверждать, что событие доходит до второго клиента. Ручная синхронизация и инкрементальный sync остаются рабочими путями.
9. **Токены не зашифрованы отдельно.** Они лежат в приватных `SharedPreferences`, backup отключён. Для повышенных требований нужен EncryptedSharedPreferences/Keystore.
10. **Нет release-сборки.** `assembleRelease`, keystore и minify не настроены.
11. **Нет CI.** Remote настроен, но сборка, тесты и lint выполняются только локально.
12. **`local.properties` привязан к `/home/quanysh/android-sdk`.** На другой машине путь и публичные параметры Supabase нужно задать заново.
13. **Офлайн-каталог проверен unit-тестами и пользователем частично.** Пользователь подтвердил офлайн-режим этапа 4; на APK `0.5.0` отдельно не проверены перезапуск без сети, индикатор сети и автоматический догон после reconnect. Кэш профиля действует 30 дней; при `isOffline` кнопки изменения скрыты, а сохранение без сети показывает ошибку и сохраняет введённые значения.
14. **Первый sync всё ещё читает весь каталог.** Полный снимок выполняется только при отсутствии курсора или пустой локальной таблице; последующие обновления инкрементальные. Для очень больших каталогов первый вход и восстановление после очистки кэша остаются тяжёлыми.
15. **Legacy-товары выгружаются автоматически при первом входе.** Если в Room остались товары, созданные до подключения Supabase, они будут созданы в общем каталоге. При совпадении активного штрихкода серверная запись имеет приоритет, локальный дубликат удаляется из кэша.
16. **Legacy-товары сохраняют локальный UUID.** При выгрузке `create_product` получает локальный `id` в `p_id`, поэтому открытая карточка не должна потеряться, а повторная выгрузка после потерянного ответа возвращает ту же строку. Для не-UUID локальных записей сервер выдаст новый `id`; в рабочей версии Room генерирует UUID.
17. **Обычные записи из UI не повторяются автоматически.** При потере ответа сервера после успешного commit create/update/delete не повторяются, чтобы не создать дубликат. Если пользователь вручную повторит создание товара без штрихкода, возможен дубликат; для товаров со штрихкодом серверный уникальный индекс защищает. Legacy-выгрузка повторяется при следующем полном sync, но с тем же `p_id` идемпотентна (после применения `003_hardening.sql`).
18. **Realtime — только триггер, не источник данных.** Payload не применяется напрямую; после события выполняется инкрементальный sync. Если Realtime недоступен, ручное обновление и reconnect-синхронизация остаются рабочими путями.
19. **Курсор `updated_at` — не транзакционный снимок.** При редком конкурентном коммите строка с более старым `updated_at`, чем уже сохранённый курсор, может не попасть в инкрементальный запрос до следующего изменения этой строки. Для MVP это принятый компромисс; гарантированный полный снимок можно получить очисткой курсора/локальной таблицы. При живых проверках двух устройств этот сценарий нужно учитывать.

## Следующий шаг

1. Установить APK `0.5.0` на два устройства и войти администратором. Изменить товар на устройстве A — на устройстве B цена должна появиться без ручного обновления.
2. Проверить инкрементальную синхронизацию: после первого полного снимка повторное открытие каталога не скачивает весь каталог; время последней синхронизации обновляется.
3. Проверить режим полёта: перезапуск без сети, каталог и поиск из Room, индикатор «Нет связи», скрытие редактирования; затем вернуть сеть и убедиться в автоматическом обновлении.
4. Отдельным шагом применить `202611100003_hardening.sql` и проверить деактивацию сотрудника, смену роли и RLS-отказы на живом JWT.
5. После живой проверки этапа 5 решать, нужен ли WorkManager для фоновой синхронизации и очередь офлайн-записей. Публичный anon/publishable key допустим в локальной конфигурации; Service Role key, PAT и пароль администратора — только в локальном `supabase_admin.env`, никогда в APK/Git.
